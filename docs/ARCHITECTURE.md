# Carza — Foundation Architecture (Phase 1)

Status: **draft for approval** · Owner: Mahdy · Last updated: 2026-10-24

This document defines the base every Phase 1 feature sits on. It covers the repo layout, the schema and its
RLS rules, auth, the app patterns, and the order we build it in. It does not specify the features
themselves (search UI, inventory CRUD, and so on). Those get their own `build-feature` plans later.

> Placeholders until you decide:
>
> - **Launch metro:** `{{METRO}}`. Seed data is generated around one center point (`seed.sql` top), so changing the city is a one-line edit.
> - **Market assumptions:** USD, miles, US addresses (ZIP, state). Say so if any of that is wrong.

Internal packages are **"just-in-time"**. They export TypeScript source (`"exports": {".": "./src/index.ts"}`),
and Next compiles them via `transpilePackages`. There's no build step, no `dist/`, and no watch mode, and Expo's Metro
can consume the same source later.

## 2. Database schema (Phase 1)

Conventions (enforced in review):

- `uuid` PKs (`gen_random_uuid()`), `created_at`/`updated_at timestamptz not null default now()`, and a shared `set_updated_at()` trigger.
- Every table has `enable row level security` and **separate policies per operation**. No `using (true)` on writes.
- Policies call `(select auth.uid())` (wrapped so Postgres evaluates it once per query).
- Helper functions are `security definer`, `set search_path = ''`, `stable`, and fully schema-qualified. They live in a **`private` schema** that the Data API doesn't expose, so policies can call them but nobody can call them over HTTP. Only the intended RPCs live in `public`.
- Every table starts with `revoke all … from anon, authenticated`, then grants exactly what's needed (often column by column). Grants and RLS are two separate layers.
- Money: `price_cents bigint`. Distances: meters in the DB, miles in the UI (conversion in `@carza/shared`).
- Status transitions that have rules (test drives, dealer verification) go through **RPC functions**.
  The table itself doesn't grant `update` on those columns.
- Column-level `grant update (col, …)` locks privileged columns (`profiles.role`, `dealerships.verification_status`).

Extensions: `postgis` (schema `extensions`), `btree_gist` (no-double-booking constraint). Usernames, slugs and invite emails are stored lowercase (enforced by CHECK), so no `citext` is needed.

### 2.2 Make/model lookup: tables, not enums

`vehicle_makes(id smallint identity, name text unique, slug unique)` and
`vehicle_models(id int identity, make_id → vehicle_makes on delete restrict, name text, slug, unique(make_id, slug))`.
These are seeded **in a migration** (they're reference data and prod needs them too): about 45 US-market makes and about 450 models.

- RLS: anyone can `select`; nobody can write through the API (no insert/update/delete policies). New models are added by migration.
- Why tables rather than enums: we need facets ("Toyota → models"), slugs for SEO URLs, and the list grows yearly. Enums can't be removed from and are awkward to extend.
- Why `vehicles` references ids rather than free text: clean facets/filters, no "Chevy/Chevrolet/chevrolet" mess. CSV import maps text → id (case-insensitive, slug, small alias map) and reports unmatched rows.

### 2.3 Tables

#### `profiles` (1:1 with `auth.users`)

| Column                 | Type                                             | Notes                                                                                                                                                |
| ---------------------- | ------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| id                     | uuid PK → `auth.users(id)` **on delete cascade** |                                                                                                                                                      |
| username               | text unique not null                             | `^[a-z0-9_]{3,30}$` (lowercase enforced). Trigger generates one from the display name + random suffix. **Never from the email**, which would leak it |
| display_name           | text not null                                    | 1–60 chars                                                                                                                                           |
| avatar_path            | text null                                        | key in `avatars` bucket                                                                                                                              |
| bio                    | text null                                        | ≤ 500                                                                                                                                                |
| city, region           | text null                                        | public, e.g. "Austin", "TX"                                                                                                                          |
| role                   | app_role default `user`                          | not updatable by users (column grants)                                                                                                               |
| created_at, updated_at | timestamptz                                      |                                                                                                                                                      |

- **Created by** an `after insert on auth.users` trigger (`handle_new_user`, security definer). It uses `raw_user_meta_data` `full_name`/`name` from Google/Apple and falls back to the email local part.
- **RLS:** `select` for anyone (every column in this table is public by design). `update` only own row, and only the columns granted (`username, display_name, avatar_path, bio, city, region`). No `insert`/`delete` (the trigger inserts; deleting the auth user cascades).

#### `profile_private` (owner-only, 1:1)

| user_id PK → profiles **on delete cascade** · postal_code text · location geography(Point) (ZIP centroid = default search center) · updated_at |

- Created by the same signup trigger. **RLS:** `select`/`update` own row only, with no other access.
- Why a separate table instead of column grants or a security-definer view: column `select` grants break `select *`, and definer views get flagged by the Supabase advisor. A second table is boring and obviously correct.
- Index: GIST `location`.

#### `dealerships`

| Column                                                  | Type                                   | Notes                                                                                                     |
| ------------------------------------------------------- | -------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| id                                                      | uuid PK                                |                                                                                                           |
| slug                                                    | text unique not null                   | lowercase `^[a-z0-9-]+$`, public URL                                                                      |
| name                                                    | text not null                          |                                                                                                           |
| description                                             | text null                              | ≤ 2000                                                                                                    |
| phone, email, website                                   | text null                              | public business contact                                                                                   |
| address_line1, address_line2, city, region, postal_code | text                                   | public (businesses)                                                                                       |
| location                                                | geography(Point) not null              | exact. Dealer addresses are public                                                                        |
| timezone                                                | text not null                          | IANA, e.g. `America/Chicago`. Checked against `pg_timezone_names`. **Test drive times render in this tz** |
| logo_path                                               | text null                              | `dealership-logos` bucket                                                                                 |
| verification_status                                     | verification_status default `pending`  | admin only                                                                                                |
| verified_at                                             | timestamptz null                       |                                                                                                           |
| created_by                                              | uuid → profiles **on delete set null** |                                                                                                           |
| created_at, updated_at                                  |                                        |                                                                                                           |

- **Created only via RPC `apply_for_dealership(...)`** (security definer). It inserts the dealership as `pending` and the caller as `owner` in one transaction, and limits each user to 1 pending application.
- **RLS:** `select` for anyone where `verified`; members can always see their own; admins see all. `update` for members with role ≥ `admin`, on granted columns only (not `verification_status`, `verified_at`, `slug` after verification). No `insert` (RPC only), no `delete` (suspend instead).
- **Verification:** `set_dealership_verification(id, status)` RPC, callable by `profiles.role = 'admin'` only. Until there's an admin UI, you run it from the SQL editor. A trigger sends a `dealership_verified`/`rejected` notification to owners.
- Indexes: `slug` unique, GIST `location`, `verification_status`.

#### `dealership_members`

| Column        | Type                                     | Notes   |
| ------------- | ---------------------------------------- | ------- |
| dealership_id | uuid → dealerships **on delete cascade** | PK part |
| user_id       | uuid → profiles **on delete cascade**    | PK part |
| role          | dealer_role not null                     |         |
| created_at    | timestamptz                              |         |

- **RLS:** `select` for members of the same dealership. `insert` only via `accept_dealership_invitation` RPC. `update` (role change) and `delete` (remove) by owner/admin. Admins can't touch owners, and the last owner can't be removed or demoted (trigger guard). A member can delete their own row (leave), except the last owner.
- Index: `(user_id)` for "my dealerships".
- Helper: **`private.is_dealership_member(dealership_id uuid, min_role dealer_role default 'staff') returns boolean`** (security definer, stable; compares roles by enum order). Used by nearly every dealer policy.

#### `dealership_invitations` (needed for `/dealer/[id]/team`)

| id uuid PK · dealership_id → dealerships on delete cascade · email text (lowercase) · role dealer_role check (≠ owner) · invited_by → profiles on delete set null · token_hash text unique · expires_at timestamptz (7 days) · accepted_at timestamptz null · created_at |

- **RLS:** `select`/`insert`/`delete` by dealership owner/admin. The invitee accepts via `accept_dealership_invitation(token)` RPC, which checks the token hash, expiry, and that `auth.email()` matches the invited email. The plain token goes only in the email.
- Unique partial index: one open invite per `(dealership_id, email)`.

| Column                                          | Type                                          | Notes                                                                                                                            |
| ----------------------------------------------- | --------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| id                                              | uuid PK                                       |                                                                                                                                  |
| owner_user_id                                   | uuid → profiles **on delete cascade** null    | exactly one owner…                                                                                                               |
| owner_dealership_id                             | uuid → dealerships **on delete cascade** null | …enforced by `check (num_nonnulls(owner_user_id, owner_dealership_id) = 1)`                                                      |

| make_id                                         | smallint → vehicle_makes **restrict**         |                                                                                                                                  |
| model_id                                        | int                                           | composite FK `(make_id, model_id) → vehicle_models(make_id, id)`, so the model must belong to the make (declarative, no trigger) |
| trim                                            | text null                                     |                                                                                                                                  |
| mileage                                         | integer not null                              | ≥ 0, ≤ 2,000,000                                                                                                                 |

#### `listings`

| Column                 | Type                                          | Notes                                                                                                                                                                                                                                                         |
| ---------------------- | --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| id                     | uuid PK                                       |                                                                                                                                                                                                                                                               |
| vehicle_id             | uuid → vehicles **on delete cascade**         |                                                                                                                                                                                                                                                               |
| seller_user_id         | uuid → profiles **on delete cascade** null    |                                                                                                                                                                                                                                                               |
| seller_dealership_id   | uuid → dealerships **on delete cascade** null |                                                                                                                                                                                                                                                               |
|                        |                                               | `check (num_nonnulls(seller_user_id, seller_dealership_id) = 1)`. Composite FKs `(vehicle_id, seller_user_id) → vehicles(id, owner_user_id)` and `(vehicle_id, seller_dealership_id) → vehicles(id, owner_dealership_id)` force the seller to own the vehicle |
| status                 | listing_status default `draft`                |                                                                                                                                                                                                                                                               |
| condition              | listing_condition default `used`              |                                                                                                                                                                                                                                                               |
| price_cents            | bigint not null                               | > 0, ≤ $10M                                                                                                                                                                                                                                                   |
| description            | text null                                     | ≤ 5000                                                                                                                                                                                                                                                        |
| stock_number           | text null                                     | dealers; unique per dealership when present (CSV re-import upserts on it)                                                                                                                                                                                     |
| location               | geography(Point) not null                     | **public point**: dealer → dealership location; private seller → approximate (see below)                                                                                                                                                                      |
| city, region           | text not null                                 | display                                                                                                                                                                                                                                                       |
| published_at, sold_at  | timestamptz null                              | set by trigger on status change                                                                                                                                                                                                                               |
| created_at, updated_at |                                               |                                                                                                                                                                                                                                                               |

- **Private-seller location privacy.** The exact point lives in `listing_private_locations(listing_id PK → listings on delete cascade, location geography, postal_code)`, readable only by the seller. Public `listings.location` is computed by the server (`@carza/shared/logic/geo.approximatePoint`), which snaps to a ~1.5 km grid cell center. We never show a map pin closer than that. RLS on `listing_private_locations`: owner-only for all operations.
- **One live listing per vehicle:** unique partial index on `vehicle_id where status in ('draft','active','pending')`.
- **RLS:**
  - `select`: anyone, when `status in ('active','pending','sold')` **and** (private seller, or the dealership is `verified`). The seller (or dealership members) can always see their own, including drafts and removed. Admins see all.
  - `insert`: `seller_user_id = auth.uid()`, or `is_dealership_member(seller_dealership_id,'staff')`. **with check:** if it's a dealer listing and `status <> 'draft'`, the dealership must be `verified`. This is the "unverified dealers can't publish" rule, enforced in the DB.
  - `update`: the same predicates in `using` and `with check` (so you can't move a listing to someone else, or publish while unverified).
  - `delete`: only `draft` listings, by their seller. Everything else goes `removed`.
- **Indexes (search):** GIST `(location)`; `(status, published_at desc)`; `(price_cents) where status='active'`; `(seller_user_id)`, `(seller_dealership_id, status)`; unique `(seller_dealership_id, stock_number)`.

#### `listing_photos`

| id uuid PK · listing_id → listings **on delete cascade** · storage_path text unique · position smallint (0–29) · width, height int · created_at |

- `unique (listing_id, position) deferrable initially deferred` (reorder in one transaction). Max 30 photos (trigger).
- **RLS:** `select` if the parent listing is visible to you (`exists (select 1 from listings …)`, which inherits listing RLS). `insert`/`update`/`delete` if `can_manage_listing(listing_id)`.

#### `saved_listings`

| user_id → profiles on delete cascade · listing_id → listings on delete cascade · created_at · PK (user_id, listing_id) |

- **RLS:** own rows only (select/insert/delete). Index `(listing_id)` for future "N people saved this".

#### `conversations`, `conversation_participants`, `messages`

`conversations`
| id uuid PK · listing_id → listings **on delete set null** · dealership_id → dealerships **on delete cascade** null · created_by → profiles on delete set null · last_message_at timestamptz · dealership_last_read_at timestamptz · created_at · updated_at |

`conversation_participants`
| conversation_id → conversations on delete cascade · user_id → profiles on delete cascade · last_read_at timestamptz · last_emailed_at timestamptz · archived_at timestamptz · PK (conversation_id, user_id) |

`messages`
| id uuid PK · conversation_id → conversations on delete cascade · sender_id → profiles **on delete set null** · body text (1–4000) · created_at |

The model:

- **Consumer↔consumer:** 2 participant rows, `dealership_id` null.
- **Consumer↔dealer:** 1 participant row (the consumer) plus `dealership_id`. **Every member of that dealership** can see it, so leads survive staff turnover. Messages sent by staff display as the dealership. The dealer side's read state is tracked once per conversation (`dealership_last_read_at`).
- Conversations are started **only via `start_conversation(listing_id, body)` RPC**. It finds or creates the conversation for (listing, buyer), refuses messaging yourself, requires the listing be visible and not `removed`, and inserts the first message atomically. Phase 1 has no cold DMs from profiles; every conversation starts from a listing, which cuts spam. (`listing_id` becomes null if the listing is ever hard-deleted, so history survives.)
- **RLS:**
  - conversations: `select` if participant or `is_dealership_member(dealership_id)`. No direct insert/delete. `update` limited to read markers via RPC `mark_conversation_read`.
  - participants: `select` if you can see the conversation. `update` own row's `archived_at`/`last_read_at` only.
  - messages: `select` if you can see the conversation. `insert` if `sender_id = auth.uid()` and you're a participant or dealership member. **No update/delete** (scam evidence must stay intact).
- Trigger on message insert: bump `conversations.last_message_at`, and create `new_message` notifications for the _other_ side (participants ≠ sender; for dealer convos, all members except the sender, or the consumer when staff sent it).
- **Realtime:** `alter publication supabase_realtime add table public.messages`. Postgres-changes delivery respects RLS, so clients only receive rows they can `select`. Nothing else is published.
- Indexes: `messages(conversation_id, created_at desc)`, `conversations(dealership_id, last_message_at desc)`, `conversation_participants(user_id)`, unique `(listing_id, created_by)` on conversations.

#### `test_drive_requests` (dealer listings only)

| Column                      | Type                                  | Notes                                                                                              |
| --------------------------- | ------------------------------------- | -------------------------------------------------------------------------------------------------- |

| requester_id                | uuid → profiles on delete cascade     |                                                                                                    |

| duration_minutes            | smallint default 30                   | 15–120                                                                                             |
| status                      | test_drive_status default `requested` |                                                                                                    |
| requester_note, dealer_note | text null                             | ≤ 1000                                                                                             |
| created_at, updated_at      |                                       |                                                                                                    |

- **Timezone safety:** everything is `timestamptz` (absolute instants). The UI renders in the **dealership's IANA timezone** with the zone label ("Sat Nov 2, 10:00 AM CDT"), never the browser's. The consumer's date/time picker input is interpreted in the dealership tz by `@carza/shared/logic/time.zonedToUtc`, unit-tested across DST transitions.
- **No double-booking:** `exclude using gist (listing_id with =, tstzrange(confirmed_time, confirmed_end) with &&) where (status = 'confirmed')`.
- **Transitions only via RPC** (no update grant): `request_test_drive(listing_id, proposed_times, note)` → requested. `respond_test_drive(id, 'confirm'|'decline', time?, note?)` (dealer staff+). `cancel_test_drive(id)` (requester, or dealer). `complete_test_drive(id)` (dealer, after `confirmed_time`). Each checks the allowed from→to state and fires a notification. One open request per (listing, requester).
- **RLS `select`:** requester, or `is_dealership_member(dealership_id)`. No direct insert/update/delete.
- Indexes: `(dealership_id, status, created_at desc)`, `(requester_id, created_at desc)`, `(listing_id)`.

#### `notifications` (in-app)

| id uuid PK · user_id → profiles on delete cascade · type notification_type · data jsonb (ids + short text for rendering; no secrets) · read_at timestamptz null · created_at |

- Inserted only by security-definer triggers/RPCs. **RLS:** `select` own. `update` own, `read_at` column only. `delete` own.
- Index `(user_id, created_at desc)` plus partial `(user_id) where read_at is null` for the unread badge.
- Email is a separate concern (4.7): Server Actions send email after the write, using the same events.

#### `reports`

| id uuid PK · reporter_id → profiles on delete set null · target_type report_target · target_id uuid · reason report_reason · details text ≤ 2000 · target_snapshot jsonb · status report_status default open · resolved_by → profiles on delete set null · resolved_at · created_at |

- Polymorphic target on purpose. A `before insert` trigger copies a **snapshot** of the reported content (listing text/price/seller, message body, profile name) into `target_snapshot`, so evidence survives edits and deletion. It also checks that the target exists _and is visible to the reporter_, so nobody can probe ids.
- **RLS:** `insert` where `reporter_id = auth.uid()`. `select` own reports. Admins `select`/`update` all. Unique `(reporter_id, target_type, target_id)` against report spam.
- Index `(status, created_at)`, `(target_type, target_id)`.

#### `rate_limits` (infrastructure, not a feature)

| key text · window_start timestamptz · count int · PK (key, window_start) |

- RLS enabled with **no policies and no grants**, so it's not reachable through the API. It's used only by the internal `enforce_rate_limit(bucket)`, which is **not executable** by `anon`/`authenticated`. That function keys on `auth.uid()` itself (and refuses when it's null), reads limits from an allow-list inside the function, and raises SQLSTATE `CZ429` when over the limit. It deletes expired windows opportunistically.
- **Called from inside the DB**: `before insert` triggers on `messages`, `listings`, `listing_photos`, `reports`, and inside the `start_conversation`/`request_test_drive`/`apply_for_dealership`/invitation RPCs. Because users can call the Supabase API directly with their own token, bypassing our Server Actions, a limit in the app layer alone would be decorative. See 4.8.

### 2.4 Storage buckets

| Bucket             | Public read | Path                           | Limits                                    | Write policy                                                                       |
| ------------------ | ----------- | ------------------------------ | ----------------------------------------- | ---------------------------------------------------------------------------------- |
| `listing-photos`   | yes         | `{listing_id}/{uuid}.{ext}`    | 10 MB; jpeg/png/webp                      | `can_manage_listing((storage.foldername(name))[1]::uuid)` for insert/update/delete |
| `avatars`          | yes         | `{user_id}/{uuid}.{ext}`       | 2 MB; jpeg/png/webp                       | `(storage.foldername(name))[1] = auth.uid()::text`                                 |
| `dealership-logos` | yes         | `{dealership_id}/{uuid}.{ext}` | 2 MB; jpeg/png/webp (no SVG: script risk) | `is_dealership_member(…,'admin')`                                                  |

- Size/MIME limits are set **on the bucket** (server-enforced by Storage) and validated again in Zod before upload.
- Filenames are always server-generated UUIDs. Users can't choose paths, so they can't overwrite someone else's object.
- Why public buckets: CDN-cacheable, `next/image`-friendly URLs, and the photos are public anyway once listed. Trade-off: draft listing photos are reachable if someone guesses a UUID path, which isn't practical.
- Orphan cleanup (photo uploaded, listing never saved) is deferred and logged as a risk.

### 2.5 Radius search

`public.search_listings(...)` with typed, named, defaulted args (so the generated TS types are precise), `security invoker` so listing RLS still applies:

- Inputs: `lat, lng, radius_miles (≤ 500)`, `make_id, model_id, year_min/max, price_min/max, mileage_max, body_styles[], drivetrains[], fuel_types[], transmissions[], condition, seller_type ('private'|'dealer'|null)`, `sort ('relevance'|'newest'|'price_asc'|'price_desc'|'mileage_asc'|'year_desc'|'distance')`, `limit (≤ 48)`, `offset (≤ 1000)`.
- Core predicate: `ST_DWithin(l.location, ST_MakePoint(lng,lat)::geography, radius_m)`, which uses the GIST index. Distance is returned as `ST_Distance(...)` in meters.
- Returns card-shaped rows: listing + vehicle + make/model names + first photo path + seller name/type + `distance_m` + `total_count` (window count, capped).
- One metro is a few thousand active rows, so a join plus GIST plus offset pagination is plenty. Keyset pagination and a denormalized search table are documented as the scale path (Risks).
- The same Zod schema (`@carza/shared/schemas/search`) parses URL search params on the web and will parse app params on mobile.

## 3. Auth & authorization

### 3.1 Supabase Auth + `@supabase/ssr`

- **Providers:** email/password (confirm email **on**), Google, Apple. Account linking by verified email is Supabase's default.
- **Where auth calls run:** sign-in, sign-up, OAuth start, and the reset request run **in the browser** via the browser client. Supabase Auth's per-IP rate limits then apply to the real user IP. If they ran in Server Actions, every user would share Vercel's IP and one bucket. Code exchange (`/auth/callback`) and OTP verify (`/auth/confirm`) are Route Handlers.
- **Three clients** in `apps/web/src/lib/supabase/`: `browser.ts` (`createBrowserClient`), `server.ts` (`createServerClient` + `cookies()`), `proxy.ts` (`updateSession` for the proxy).
- **Keys:** new-style `sb_publishable_…` (browser-safe) and `sb_secret_…` (server-only). The secret key is used **only** by the email/admin paths that RLS can't express, and it's imported in a file guarded with `import 'server-only'`.

### 3.2 Proxy (Next 16's `proxy.ts`, formerly middleware)

1. Refresh the session (`supabase.auth.getClaims()`, which verifies the JWT locally against the JWKS) and write refreshed cookies onto the response.
2. Guard: `/account/**` and `/dealer/**` with no valid claims → `302 /sign-in?next=<path>`. Signed-in users on `/sign-in`/`/sign-up` → `/`.
3. Generate the per-request CSP nonce and set security headers (4.9).

- Membership/role checks are **not** done in the proxy (no DB round-trip per request). They're done in layouts and in every action.

### 3.3 Server helpers (`apps/web/src/lib/auth.ts`)

```ts
getUser(): Promise<User | null>                     // React cache()'d per request; supabase.auth.getUser()
requireUser(): Promise<User>                         // redirect('/sign-in?next=…') in pages; ActionError('UNAUTHENTICATED') in actions
requireDealerMember(dealershipId, minRole = 'staff') // requireUser + is_dealership_member RPC; notFound() / ActionError('FORBIDDEN')
requireAdmin()                                       // profiles.role = 'admin'
```

- CLAUDE.md requires `getUser()` on the server. We keep that for these helpers because it's authoritative and catches revoked sessions. The proxy uses `getClaims()` because it's cheaper. Both are safe; `getSession()` is never used for authorization.
- `safeNextPath(next)` in `@carza/shared` accepts only same-origin relative paths (`/x`, not `//x`, not `/\x`, no scheme) and is unit-tested. Every `next=` and OAuth `redirectTo` goes through it, which closes the open-redirect hole.
- **RLS is the real guard.** Helpers give fast, friendly failures; the DB refuses regardless.

### 3.4 Becoming a dealer

1. A signed-in user opens `/dealer/apply`, fills in business details (name, address → geocoded point, phone, website, timezone). Server Action → `apply_for_dealership` RPC → dealership `pending` + user `owner`.
2. The dashboard works immediately in **pending** mode: they can set up the profile, invite team members, and create **draft** listings and CSV-import as drafts. A banner says "Pending verification: listings go live once verified".
3. You verify (SQL editor: `select set_dealership_verification('<id>','verified')`). The owner gets an in-app notification and email. Now they can publish.
4. `rejected`/`suspended`: dealer listings drop out of public `select` immediately (RLS), and the dealer page 404s.

- Geocoding address → point: Phase 1 uses the **free US Census geocoder** or a ZIP-centroid table. See Open questions.

## 4. App foundations

### 4.1 Data access pattern

- **Reads:** Server Components call `@carza/db` query helpers with the request-scoped server client (RLS applies as the user). No client-side fetching for initial data.
- **Writes:** **Server Actions only**, always via `action()` (4.2). Forms use `useActionState`, and progressive enhancement works without JS for simple forms.
- **Client-side Supabase** is used for only three things: (1) auth calls (3.1), (2) Realtime subscriptions to `messages`, (3) direct Storage uploads with a path the server issued.
- **Route Handlers** only when something outside our React tree calls us: `/auth/callback`, `/auth/confirm`, `sitemap`/`robots` (metadata routes), and later webhooks (Resend events), the CSV import progress if it needs streaming, and the mobile app if it needs a non-Supabase endpoint.
- No `fetch` to our own API from Server Components. No tRPC/GraphQL layer.

### 4.2 The `action()` wrapper

```ts
// packages/shared/src/result.ts
export type ActionResult<T> =
  | { ok: true; data: T }
  | { ok: false; error: { code: ErrorCode; message: string; fieldErrors?: Record<string, string[]> } };
export type ErrorCode = 'UNAUTHENTICATED' | 'FORBIDDEN' | 'VALIDATION' | 'NOT_FOUND' | 'RATE_LIMITED' | 'CONFLICT' | 'INTERNAL';

// apps/web/src/lib/action.ts
export const createListing = action(
  { schema: createListingSchema, auth: 'required' },
  async (input, { user, supabase }) => { … return { id }; },
);
```

Steps the wrapper performs, in order:

1. Zod `safeParse(rawInput)` → `VALIDATION` with `fieldErrors` (flattened) on failure.
2. Auth (`required` | `optional`) via `getUser()` → `UNAUTHENTICATED`.
3. Run the handler with `{ user, supabase }`.
4. Catch: a thrown `ActionError(code, message)` passes through as-is. A Postgres error is mapped (`42501`/RLS → `FORBIDDEN`, `23505` → `CONFLICT`, `23P01` exclusion → `CONFLICT` "That time was just booked", `CZ429` → `RATE_LIMITED`, `P0001` from our RPCs → its message, which we author). **Anything else → `INTERNAL` "Something went wrong"** plus a server log with a correlation id, which is included in the message so support can find it.

- Never throws to the client and never leaks stack traces or SQL text. `redirect()`/`notFound()` are re-thrown (Next control flow).
- Also accepts `FormData` (converted with a small `formDataToObject` helper) so `<form action>` works.

### 4.3 Errors, loading, empty states, toasts

- Every route segment that fetches has `loading.tsx` (skeleton matching the layout) and `error.tsx` (friendly message + retry + correlation id). There's a root `not-found.tsx` and a `global-error.tsx`.
- Shared `<EmptyState icon title body action/>` and `<ErrorState/>` components. Every list page must render one (code-review checklist item).
- **Toasts:** `sonner`. Pattern: forms show field errors inline, and toast only for non-field outcomes ("Listing published", "Couldn't send. Try again").
- Server-side redirect-with-message uses a short-lived `flash` cookie read by the layout and shown as a toast once.

### 4.4 Env validation

- `apps/web/src/env.ts`: two Zod objects, `server` (`SUPABASE_SECRET_KEY`, `RESEND_API_KEY`, `EMAIL_FROM`) and `client` (`NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `NEXT_PUBLIC_SITE_URL`). Client vars are referenced as literal `process.env.NEXT_PUBLIC_…` so Next inlines them.
- `next.config.ts` imports `env.ts` → **`next build` fails** with a readable list of missing or invalid vars. The server object is exported from a `server-only` module, so importing it into a client component is a build error.
- No dependency: about 40 lines of Zod instead of `@t3-oss/env-nextjs`.
- `.env.example` is updated to the new key names (`NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SECRET_KEY`). The legacy `anon`/`service_role` names are retired.

### 4.5 UI system

- **Tailwind v4** (CSS-first). Tokens live in `packages/config/tailwind/theme.css` (`@theme` + CSS variables for light/dark: background, foreground, primary, muted, accent, destructive, border, ring, radius, chart colors, plus brand). `apps/web/src/app/globals.css` does `@import "tailwindcss"; @import "@carza/config/tailwind/theme.css";`.
- **shadcn/ui** (copied components in `components/ui`, which we own). We start with button, input, label, textarea, select, checkbox, dialog, sheet, dropdown-menu, avatar, badge, card, skeleton, separator, tabs, tooltip, sonner, and form helpers. More are added per feature.
- **Dark mode:** `next-themes` (class strategy, system default, no flash).
- **Layout:** mobile-first. Public shell = sticky header (logo, search, Sell button, account menu / sign-in) + bottom tab bar on mobile (Home, Search, Sell, Messages, Account) + footer. Dealer shell = collapsible sidebar (Dashboard, Inventory, Leads, Test drives, Team, Settings) → `Sheet` on mobile, plus a dealership switcher and a pending-verification banner.
- Accessibility: Radix primitives, visible focus rings, 44px touch targets, `eslint-plugin-jsx-a11y` (comes with eslint-config-next).

### 4.6 Images

- Uploads: the client resizes to ≤ 2048px long edge and re-encodes to WebP (canvas, with no library) → asks a Server Action for an upload path (it checks `can_manage_listing`, count < 30, and rate limit) → uploads directly to Storage with the browser client (Storage RLS enforces the path) → a Server Action records `listing_photos` rows.
- Display: `next/image` with `remotePatterns` restricted to `<ref>.supabase.co/storage/v1/object/public/**` (and `127.0.0.1:54321` in dev). We use Next's optimizer rather than Supabase image transforms (those need the Pro plan). This is a cost check for later.
- Limits (shared constants): 10 MB raw input, jpeg/png/webp/heic-from-iOS (iOS Safari hands over JPEG), 30 photos per listing, 2 MB for avatars/logos.

### 4.7 Email

- `apps/web/src/lib/email/send.ts`: `sendEmail({ to, template, props })`, `server-only`. It wraps Resend, renders a React Email template, and is a no-op that logs in dev/test when `RESEND_API_KEY` is unset (the key is optional in `env.ts` outside production).
- Templates (`src/emails/`): `welcome`, `new-message` (sender name + 140-char preview + link, never the full body), `test-drive-requested` (to dealer), `test-drive-confirmed` (to requester, time rendered in the dealership tz), `dealership-verified`, and `dealership-invite`.
- Sending is done in the Server Action **after** the DB write using Next's `after()`, so it never slows or fails the user's request. **Message emails are throttled:** at most one per conversation per recipient per 15 min, and only if the message is still unread (`conversation_participants.last_emailed_at`).
- Auth emails (confirm/reset) are sent by **Supabase via Resend SMTP**, not by our code.

### 4.8 Rate limiting

- **Auth:** Supabase Auth's built-in per-IP limits (they work because auth calls come from the browser), plus optional Turnstile CAPTCHA.
- **App writes:** a Postgres fixed-window limiter enforced **inside the database** by triggers and RPCs (2.3). It's keyed on `auth.uid()`, so it can't be spoofed, and it can't be skipped by calling the Supabase API directly. `action()` just maps `CZ429` to `RATE_LIMITED`. Initial buckets:
  - `message_send` 30/min and 300/day · `conversation_start` 10/hour and 30/day · `listing_create` 10/day (private), 1000/day (dealer listings, keyed per user, for CSV) · `photo_upload` 200/hour · `test_drive_request` 5/hour and 10/day · `report_create` 20/day · `dealer_apply` 3/day · `invite_send` 50/day.
- Why Postgres rather than Upstash/Redis: no new vendor or dependency, it's transactional with our data, and at one-metro scale a Postgres write per action is nothing. Swap path: same `enforce_rate_limit` interface backed by Upstash if we ever need it.

### 4.9 Security headers + CSP

Set in `proxy.ts` (CSP needs a per-request nonce) and `next.config.ts` `headers()` for the static ones:

- `Content-Security-Policy`: `default-src 'self'; script-src 'self' 'nonce-{n}' 'strict-dynamic'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob: https://<ref>.supabase.co; connect-src 'self' https://<ref>.supabase.co wss://<ref>.supabase.co; font-src 'self'; frame-ancestors 'none'; form-action 'self' https://accounts.google.com https://appleid.apple.com; base-uri 'self'; object-src 'none'; upgrade-insecure-requests`. Report-only in the first preview, enforced once clean.
- `Strict-Transport-Security: max-age=63072000; includeSubDomains; preload`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy: camera=(), microphone=(), geolocation=(self)`, `X-Frame-Options: DENY`.
- Trade-off: nonce CSP makes every page dynamically rendered. That's acceptable because pages are session-aware anyway (header state), and Supabase reads are fast. Revisit with Next's SRI/static CSP if listing pages need caching at scale.

### 4.10 Logging & monitoring (recommendation only, nothing installed)

- **Now:** structured `logger.ts` (JSON lines with level, correlation id, and user id, never PII or bodies) → Vercel runtime logs. Supabase logs/advisors via the dashboard.
- **Recommend before launch:** **Sentry** (`@sentry/nextjs`) for errors + traces, with PII scrubbing on. Its free tier is enough for one metro. Alternative: Vercel Observability Plus if you'd rather avoid another vendor. Add Vercel Web Analytics for traffic (no cookies).

### 4.11 SEO basics

- Root `metadata` (title template `%s · Carza`, description, `metadataBase` = `NEXT_PUBLIC_SITE_URL`).
- `/listings/[id]`: `generateMetadata` → "2019 Toyota Tacoma TRD Off-Road · $34,500 · Austin, TX". OpenGraph/Twitter use the first photo. **JSON-LD** `Vehicle` + `Offer`. `noindex` when not active.
- `/dealers/[slug]`: `AutoDealer` JSON-LD.
- `sitemap.ts`: home, search, active listings (up to 50k), verified dealers. `robots.ts`: disallow `/account`, `/dealer`, `/auth`, `/api`, and preview deployments disallow all.
- Canonical URLs on search (normalized param order).

## 6. Build order

Each stage is its own branch and PR, green on its own, and merged before the next starts. Every stage runs `security-auditor` + `code-reviewer`, fixes all Critical/High findings, and ships via `/ship`.

## 7. Decisions & risks

### Decisions you should know about

1. **Next 16 `proxy.ts`** instead of `middleware.ts`. Same idea, renamed in Next 16, and it runs on the Node runtime.
2. **New Supabase API keys** (publishable/secret) instead of anon/service_role. `.env.example` is renamed accordingly.
3. **Auth calls from the browser**, not Server Actions, so Supabase's per-IP auth rate limits actually work (3.1).
4. **All app writes via Server Actions** even though RLS would allow direct client writes. That gives one place for validation, rate limits, and email side effects, and RLS still backs it up.
5. **Status machines via RPC** (test drives, verification, invitations, conversation start) instead of trusting UPDATE policies. Fewer ways to put a row in an illegal state.
6. **Separate `vehicles` table** owned by a user or dealership (XOR), VIN not unique.
7. **Make/model as lookup tables** seeded by migration, not enums or free text.
8. **Private-seller exact location in its own owner-only table**. The public point is snapped to a ~1.5 km grid.
9. **Postgres rate limiter** instead of Upstash (no new vendor).
10. **Dealer conversations belong to the dealership**, not to one employee.
11. **Conversations start only from a listing** (no cold DMs) in Phase 1.
12. **Handwritten env validation** with Zod instead of `@t3-oss/env-nextjs`.
13. **Internal packages ship TS source** (no build step).
14. **Nonce-based CSP** means pages render dynamically.
15. **Next image optimizer** rather than Supabase image transforms (Pro plan).

Rejected alternatives: Prisma/Drizzle (they'd duplicate RLS-aware access; supabase-js + generated types is enough). tRPC (Server Actions cover it). Upstash (vendor). Algolia/Typesense for search (overkill for one metro; PostGIS covers radius). Clerk/NextAuth (Supabase Auth is integrated with RLS). Storing photos in Vercel Blob (Storage RLS is the point).

### Top 5 risks

| #   | Risk                                                                                                                                   | Mitigation                                                                                                                                                                                                                                                                                                  |
| --- | -------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **RLS mistakes leak private data** (messages, exact locations, drafts)                                                                 | Per-table allow/deny test matrix in CI. Privileged writes via audited RPCs. `security-auditor` every stage. Supabase advisors after each apply. Private columns live in separate tables or views, never "hidden in the UI"                                                                                  |
| 2   | **Auth email deliverability / OAuth misconfig** blocks sign-ups (default SMTP, Apple secret expiry, redirect URL mismatch on previews) | Resend SMTP is in the checklist. Wildcard preview redirect URLs. 6-month Apple reminder. Stage 6 smoke test runs on a real preview                                                                                                                                                                          |
| 3   | **Scams/spam in messaging** (fake listings, off-platform payment requests)                                                             | Reports with snapshots from day one. Rate limits on conversation start and messages. Listing-only conversation start. Later: link/phone-number detection + warning banner (not in foundation)                                                                                                               |
| 4   | **Search performance or cost as inventory grows** (joins + offset pagination + image optimization)                                     | GIST and B-tree indexes from day one. Offset capped. Plans checked on seeded data in stage 2 (at 60 rows the planner prefers B-tree; GIST takes over as volume grows). Scale path documented: denormalized `listing_search` materialized table + keyset pagination. Monitor Vercel image optimization usage |
| 5   | **Timezone bugs in test drives** (DST, browser vs dealer tz)                                                                           | `timestamptz` only, rendered in the dealership's IANA tz with a label. Conversion in one shared function with DST unit tests. Exclusion constraint prevents overlapping confirmed bookings                                                                                                                  |

Also tracked (lower): orphaned storage objects (cleanup job later); Supabase free-tier pausing on dev after inactivity; the `{{METRO}}` choice affecting seed geography only.
